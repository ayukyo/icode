### 血的教训：patch 观察点（CI 连红三轮，Windows 本地全绿）

1. **重导出保不住模块内调用点**。函数 A 搬去新模块后，A 内部对 B 的调用按**新模块全局**解析；`patch.object(旧模块, "B")` 是静默 no-op——测试照绿但隔离丢失。已实证（`m.called=False`）。
2. **stdlib 模块属性被当失效 import 清理**会炸。测试经 `patch.object(runner.selectors, ...)` 观察已下沉路径，`runner` 失去该属性就 AttributeError。
3. **Windows 单平台本地回归无法证明跨平台安全**。受影响测试几乎全是 POSIX-only，Windows 上直接 skip。本机 3812 项与基线逐项一致，CI 已红三轮。

**定位方法（可复用）**：用 worktree 跑基线全量套件 → 正则提取 `^(FAIL|ERROR): (\S+) \((tests\.\w+\.\w+)\)` 与 verbose 行 → set diff 基线与改动的失败集 → 精确定位新增失败。本次据此把 9 个回归全部揪出（4 个 `_build_runner` 5 元组 mock、1 个 `_run_agent` kwargs 读取、1 个 Linux-only 解包等）。

**新增机器防线**：`PatchObservationPointTests`（stdlib 观察点）+ `InternalCallPatchTargetTests`（静态扫描拒绝把 vp 内部被调者 patch 在 runner 上）。均用「把错误改回去」验证过会失败。

**五道新增机器防线**（都验证过「把错误改回去」会失败）：

1. `PatchObservationPointTests` —— runner 不得失去被观察的 stdlib 属性（selectors/select）。
2. `InternalCallPatchTargetTests` —— 静态扫描，拒绝把 vp 内部被调者 patch 在 runner 上。
3. import 守卫 —— 用了 `verification_process` 必须 import（正则需排除 `verification_process.py` 路径字面量）。
4. `test_module_name_resolution.py` —— symtable 全量扫描模块级未定义名。**它抓出了 `icode step-run` 的真实产品缺陷**：cmd_step_run/cmd_chain 引用了作用域里不存在的 `routes` → 运行即 NameError，整条命令不可用（既存缺陷，非重构引入）。修法：`_build_runner` 一并返回 routes。
5. `test_platform_branch_reachability.py` —— **剥掉平台 skip 后跑测试体**，只判 NameError/AttributeError。**这是决定性的一道**：Windows 上 POSIX 测试一律 skip，CI 反馈又慢；剥掉 skip 后本机跑，三轮重复犯的同类错误一次性全暴露。

**教训固化**：跨平台重构里，**「代码搬走」必须同步三处**——(a) 调用点的 patch 目标、(b) 所在作用域的 import、(c) 经旧模块的 stdlib 属性访问。少同步任一处在本机都看不见。

### dependabot PR #4 失败归因（2026-10-26 上午）

PR #4（`actions/setup-python` 7.0.0→7.1.0）CI 失败 3 个 job，**与重构零关联**。取证链：

1. **代码字节相同**：`git diff main pr4merge -- src/ tests/ scripts/ native/` 为空；逐目录树哈希全部一致（`src=a2879c3dcbab`、`tests=6ce7c3a177b3`）。全仓树哈希只因 `.github/` 不同而异。
2. **三条失败各有独立成因**：
   - `Python 3.12`(ubuntu)：`test_ci_workflow_contracts` / `test_provenance_validation_budget` 断言 workflow 的**固定内容**（`setup-python@5fda3b95…` 字面量 + workflow 片段 SHA256）→ 仓库的 workflow 冻结契约在正确拦截未审阅的 workflow 变更。
   - `R3 Windows Reviewer snapshot candidate`：`scripts/windows_positive_loopback_admin_native.py:67` 要求 `GITHUB_REF=="refs/heads/main"` 且 `GITHUB_WORKFLOW_SHA==GITHUB_SHA`；`pull_request` 事件下 `GITHUB_REF=refs/pull/4/merge`、`GITHUB_SHA=<merge commit>` → `context_workflow`。这是**特权正向证据 gate 只允许从 main 触发**的安全护栏。
3. **交叉复现**：换 workflow 后 `main → 4/4 通过`、`PR → 3 失败`。

**要点**：仓库把 `.github/workflows/` 内容当作**受冻结的契约资产**（字面量 + 哈希双锁），特权证据采集限定 main。改 workflow 的 PR 必须同步更新契约常量并经审阅。**PR 红 ≠ main 红**，归因要落到文件:行号。

**取证工具链（可复用）**：
- 未认证 GitHub API 会限流；用 `git credential fill` 取 PAT 后 `curl -H "Authorization: Bearer $TOKEN"` 即可拿到 job log 与 check-run annotations（含完整 traceback）。
- `curl -sSL .../actions/jobs/<id>/logs` 下载 job 日志（需 admin 或 write 权限；PAT 可用）。
- PR 事件的实际代码是 **merge commit**：`git fetch origin pull/N/merge:prNmerge` 后比对树哈希。
